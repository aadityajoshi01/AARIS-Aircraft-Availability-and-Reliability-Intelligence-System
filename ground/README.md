# AARIS — Ground Station

Standalone FastAPI service that receives the JSON health reports produced by
`edge/edge_node.py`, maintains fleet state in **SQLite** (`ground/fleet.db`),
and solves a deterministic 30-day maintenance plan with **Google OR-Tools
CP-SAT**. It never touches anything under `edge/` or `results/ridge_model/` —
reports are pure data over HTTP.

## Layout

```
ground/
  ground_station.py     FastAPI app (SQLite, Pydantic models, UTC ISO-8601)
  security.py           JWT login, static edge-device tokens, RBAC, audit events
  scheduler.py          CP-SAT 30-day maintenance planner + CLI
  fleet_config.json     90-aircraft roster (6 models x 15) -> seeds the aircraft table at startup
  aircraft_profiles.json SYNTHETIC per-aircraft demo profiles (type/role/base/
                        maintenance/issue history/report trend + a per-type
                        reference image filename) — no real IAF data
  make_profiles.py      deterministic generator for aircraft_profiles.json (seed 2026)
  requirements.txt      fastapi, uvicorn[standard], pydantic, ortools, PyJWT, python-multipart
  seed_demo.py          seeds a varied demo fleet (CRITICAL/HIGH/MEDIUM/LOW, no-spare);
                        ingests each profile's synthetic trend history as older reports,
                        then the current SEED reports (54/36 CP-SAT plan preserved)
  smoke_test.py         end-to-end test (temp DB): edge -> auth/RBAC -> ingest -> schedule
                        -> models -> alerts -> restart
  report_AC-017.json    a captured real edge report (curl fixture)
  fleet.db              created & seeded automatically on first startup
```

## Install & run

```bash
# deps are already in the repo venv; for a fresh env:
pip install -r requirements.txt

# from the ground/ directory:
../.venv/Scripts/python.exe -m uvicorn ground_station:app --reload --port 8001
```

Startup log: `Application startup complete` → `[ground] SQLite ... seeded/verified
90 aircraft; loaded 90 synthetic profiles.`

## Database

`ground/fleet.db`, six tables:

- **aircraft** — roster metadata from `fleet_config.json`
  (`aircraft_id, base, mission_priority, spare_available`) **plus the latest
  state** (`latest_rul_cycles, latest_engine_health, latest_risk,
  latest_top_issues, latest_recommended_action, latest_report_at, updated_at`).
  Seeded with `INSERT OR IGNORE`, so re-starts never clobber ingested state.
- **reports** — every ingested report, full history (`raw_payload` keeps the
  original JSON), indexed on `(aircraft_id, timestamp DESC)`.
- **maintenance_plans** — every plan generated by `POST /schedule`, persisted
  as JSON so `GET /schedule/latest` survives restarts.
- **aircraft_profiles** — one SYNTHETIC demo profile per aircraft
  (`aircraft_id, profile_json, stored_at`), upserted from
  `aircraft_profiles.json` at every startup. The scheduler never reads this
  table; it enriches `GET /fleet/{aircraft_id}` and is aggregated per aircraft
  model by `GET /models`.
- **audit_logs** — security/ops events (`timestamp, actor_id, actor_role,
  action, resource, aircraft_id, outcome, details_json`). Never contains
  tokens, passwords, or raw report payloads — see Security below.
- **alerts** — urgent critical alerts. A CRITICAL report ingested via
  `POST /ingest_report` auto-raises **one active alert per aircraft**
  (`aircraft_id, report_id, rul_cycles, engine_health, severity, message,
  status, created_at, acknowledged_at, acknowledged_by, cleared_at`); a further
  CRITICAL report refreshes the open alert rather than stacking duplicates. A
  later **strictly-newer** non-CRITICAL reading for that aircraft moves the
  alert to `CLEARED` (an out-of-order older reading never closes an open one),
  so `ACTIVE` always means "critical right now". Operators read them with
  `GET /alerts` and settle them with `POST /alerts/{id}/ack`.
  Purely additive — no existing table or response schema changed.

All timestamps are stored/returned as UTC ISO-8601, e.g. `2026-10-11T13:07:00Z`.

## Synthetic aircraft profiles (data provenance)

`aircraft_profiles.json` gives each of the 90 aircraft a realistic demo identity
(type/model_code/role/origin/engines, base, last-maintenance record, an
issue-history list, and a report trend), in 6 model blocks of 15 airframes:
RAFALE-EH (Dassault Rafale EH, AC-001..AC-015), SU30MKI (Sukhoi Su-30MKI,
AC-016..AC-030), TEJAS-MK1A (HAL Tejas Mk1A, AC-031..AC-045), MG29UPG (MiG-29UPG,
AC-046..AC-060), M2000IT (Mirage 2000I/TI, AC-061..AC-075) and JAGUAR-IM
(Jaguar IS/IM, AC-076..AC-090). It is loaded into its own
`aircraft_profiles` table at startup and surfaced through the additive
`"profile"` key on `GET /fleet/{aircraft_id}` and the per-model aggregates on
`GET /models`. **The scheduler never reads it, and
no existing response schema changed** — this is enrichment, not a behavior change.

All profile content is **clearly synthetic demonstration data**. No real Indian
Air Force maintenance records, tail numbers, sortie data, defect reports,
classified information, or real operational data are used, scraped, inferred, or
implied. Every stored profile carries `"synthetic": true`, the JSON header holds a
`data_provenance` block, and the dashboard shows a banner to the same effect.

Each profile also carries an `"image"` field (just a filename, e.g.
`"su30mki.jpg"`) pointing at a **per-type reference photo** stored under
`dashboard/assets/plane_types/`. These photos depict the aircraft *type* only —
they are not the specific fictional airframe and carry no association to any real
tail number, base or record. The dashboard resolves the filename against that
folder and omits the image gracefully if the file is missing.

Regenerate the file deterministically (seed 2026, self-checks AC-017 identity and
all three operational statuses):

```bash
# from ground/:
../.venv/Scripts/python.exe make_profiles.py
```

The RUL/engine-health numbers themselves still come from the **NASA C-MAPSS FD001**
Ridge model on the edge node; only the aircraft identities and their
maintenance/issue narratives are synthetic. AC-017 stays a Su-30MKI at
`112.76 / 90.21 / LOW`.

## Security (`security.py`)

Deny-by-default access control, deliberately small: JWT logins for humans,
static per-device bearer tokens for edge nodes, role checks as FastAPI
dependencies, and an audit trail. Existing response schemas did not change —
the only new endpoint is `POST /auth/login`, plus `Authorization: Bearer`
enforcement on the protected endpoints below.

**Actors**

- **Humans** — `POST /auth/login` (OAuth2 password form) returns a short-lived
  HS256 JWT (`{access_token, token_type, role}`, default TTL 60 min).
  Demo users (prototype-grade, as requested — replace before any real use):

  | Username     | Password       | Role                |
  |--------------|----------------|---------------------|
  | `maintainer` | `maintainer123`| `maintenance_officer` |
  | `commander`  | `commander123` | `commander`         |
  | `admin`      | `admin123`     | `admin`             |

- **Edge devices** — static bearer tokens, each bound to exactly one aircraft:
  `EDGE_<AIRCRAFT>_TOKEN`, e.g. `EDGE_AC017_TOKEN` → `AC-017`. Every aircraft in
  `fleet_config.json` is registered at startup, so the whole roster
  (AC-001…AC-090, 90 tokens) can report concurrently — that is what
  `live_reporter.py --fleet` uses. With no env var set, each aircraft falls back
  to a deterministic local-demo default (`edge-ac###-dev-token`); those are
  guessable, so the ground prints a startup warning naming the count while any
  default is in use (it never prints a token). A device token ingests reports
  **only** for its assigned aircraft; any other `aircraft_id` → 403.

**Roles × endpoints** (401 = missing/invalid/expired credentials;
403 = wrong role or device↔aircraft mismatch)

| Endpoint                | edge_device | maintenance_officer | commander | admin |
|-------------------------|-------------|---------------------|-----------|-------|
| `POST /ingest_report`   | own aircraft only | —             | —         | yes   |
| `GET /fleet`, `/fleet/{id}` | —         | yes                 | yes       | yes   |
| `GET /models`           | —           | yes                 | yes       | yes   |
| `GET /alerts`           | —           | yes                 | yes       | yes   |
| `POST /alerts/{id}/ack` | —           | yes                 | yes       | yes   |
| `POST /schedule`        | —           | yes                 | —         | yes   |
| `GET /schedule/latest`  | —           | yes                 | yes       | yes   |
| `GET /health`           | open (liveness probe) ||||

**Configuration** (repo-root `.env.example`; `.env` is gitignored):

| Variable | Purpose |
|----------|---------|
| `AEROGUARD_SECRET_KEY` | JWT signing key. Required in real use; otherwise an insecure dev default is used and a loud warning prints at startup. |
| `EDGE_<AIRCRAFT>_TOKEN` | Device token for that aircraft, e.g. `EDGE_AC017_TOKEN` for AC-017. All 90 roster entries register at startup; unset means the deterministic `edge-ac###-dev-token` demo default (startup warns about it). Set one per real device. |
| `AEROGUARD_JWT_TTL_MIN` | access-token lifetime in minutes (default 60). |
| `GROUND_HOST` | bind host when launched via `python ground_station.py` (default `127.0.0.1`; set `0.0.0.0` so a Jetson on the LAN can reach the base station — demo/local only). |
| `GROUND_PORT` | listen port for the same convenience launcher (default 8001). |

**Audit trail** — every event below lands in the `audit_logs` table:
logins (success/denied), failed authentication (missing/invalid/expired
tokens), permission denials, successful ingestions, rejected reports (422 /
not-in-roster / device mismatch, alert creation), fleet & aircraft views,
model-profile views (`models_view`), alert views (`alerts_view`) and
acknowledgements (`alert_ack`), schedule views and scheduling runs.
`smoke_test.py` asserts both that these events are recorded
and that no token/password/raw-payload material is ever logged.

## Endpoints

Every endpoint below except `POST /auth/login` and `GET /health` requires
`Authorization: Bearer <JWT or device token>` (roles per the Security table).

| Method | Path                    | Result |
|--------|-------------------------|--------|
| POST   | `/auth/login`           | **200** `{access_token, token_type: "bearer", role}` for a demo user (form-encoded `username`/`password`); bad credentials → **401**. |
| POST   | `/ingest_report`        | **201** `{report_id, state_updated, alert_created, alert_id, alert_cleared, aircraft}`. Aircraft's latest state updates only when the incoming `timestamp` is strictly newer; the report is always kept as history. A `risk: "CRITICAL"` report auto-raises/refreshes **one active alert** for that aircraft (`alert_created` true only on first). A strictly-newer non-CRITICAL report closes it (`alert_cleared` = rows closed). Device tokens: other aircraft → **403**. |
| GET    | `/fleet`                | All 90 aircraft with latest `rul_cycles, engine_health, risk, top_issues, recommended_action, latest_report_at` + metadata. |
| GET    | `/fleet/{aircraft_id}`  | Latest state + report history (`?history_limit=`, default 20) **plus an additive `"profile"` object** (the synthetic demo profile; `null` when none is loaded) — existing keys are unchanged. Unknown id → 404. |
| GET    | `/models`               | Per-aircraft-MODEL profiles for the demo fleet: `{count: 6, aircraft_total: 90, unprofiled_aircraft: 0, plan_generated_at, synthetic: true, note, models: [...]}` — the 90 airframes grouped into 6 model blocks of 15 (Rafale EH, Su-30MKI, Tejas Mk1A, MiG-29UPG, Mirage 2000I/TI, Jaguar IS/IM). Each aggregate carries `model_code, type, role, origin, engines, image, aircraft_count, aircraft_ids, reporting_count` (13 of 15), `unreported` (2), `risk_mix`/`critical` (3 CRITICAL per model), `ready_count` (12), `at_risk_count`, `avg_rul_cycles`, `avg_engine_health`, `lowest_rul_cycles`, `bases`, `spares_missing` (5), `open_issues`, `issue_systems`, `scheduled_in_plan` (9), `deferred_in_plan` (6) and `aircraft[]` (per-airframe state + `plan_status`/`plan_day`). Read-only and additive — the scheduler never reads profiles. |
| GET    | `/alerts`               | Critical alerts, newest first: `{count, status_filter, alerts:[{id, aircraft_id, report_id, rul_cycles, engine_health, severity, message, status, created_at, acknowledged_at, acknowledged_by, cleared_at}]}`. `?status=ACTIVE\|ACKNOWLEDGED\|CLEARED\|ALL` (default ACTIVE), `?limit=` (default 100). |
| POST   | `/alerts/{alert_id}/ack`| **200** `{acknowledged, already, alert}` — marks an ACTIVE alert ACKNOWLEDGED with the acting user + UTC time. Unknown id → 404; anything not ACTIVE (already acked, or auto-cleared after recovery) → `already: true`. |
| POST   | `/schedule`             | **200** with a CP-SAT plan `{generated_at, horizon_days, max_daily_maintenance, scheduled_count, deferred_count, tasks, daily_load, solver_status, plan_id}`; the plan is persisted. Optional JSON body `{"horizon_days": 1-365, "max_daily_maintenance": 1-20}` (defaults 30 / 8); out-of-range → **422**. No feasible plan → **503**. |
| GET    | `/schedule/latest`      | `{available: true, plan: {...}}` — the exact persisted plan from the last `POST /schedule`, byte-identical across service restarts. Before any schedule exists: `available: false` with an empty plan + note. |
| GET    | `/health`               | Database status/path, `aircraft_count`, `report_count`, `latest_report_at`. |

### /ingest_report contract

Accepts the exact `edge /predict` response (`report_AC-017.json` is one).
Required & validated: `aircraft_id` (must exist in the roster, else **422**),
`timestamp` (ISO-8601), `rul_cycles` (finite, 0–125), `engine_health`
(finite, 0–100), `risk` (LOW/MEDIUM/HIGH/CRITICAL). Optional passthrough:
`engine_id, top_issues, recommended_action, model, input_window_shape`.
Any violation returns **422** with a specific message (NaN/Inf inputs are
sanitized in error details, so even malformed JSON floats can't crash the
error path).

### Scheduling rules (`scheduler.py`)

- Horizon: days 1–30; at most **one task per aircraft**; at most
  **`MAX_DAILY_MAINTENANCE = 8`** aircraft maintained per day.
- Deadline: `maintenance_deadline_day = max(1, min(30, floor(rul_cycles * 0.8)))`.
  Urgent (CRITICAL/HIGH) aircraft are kept **on or before their deadline**.
- Mission priority + urgency push earlier slots: objective = per-aircraft
  weight `w = 10*urgency + 4*risk_weight*mission_priority` times scheduled
  day, plus deferral penalties (CRITICAL ≫ HIGH ≫ MEDIUM), plus a soft
  penalty for no-spare aircraft planned inside the 5-day spare lead time.
- Spare availability is honoured **only when every aircraft can still get a
  feasible on-time slot** (phase 1, hard); otherwise it becomes a soft cost
  and the plan documents the trade-off. The solver tries hard-feasible →
  soft-spare-with-deferral → past-deadline phases and reports
  `solver_status` (`OPTIMAL`/`FEASIBLE`/…).
- Deterministic: single worker, fixed random seed 7. Every aircraft appears
  exactly once as **SCHEDULED** (with `scheduled_day`, deadline, reason) or
  **DEFERRED** (with an explicit reason — LOW-risk healthy, or no telemetry
  yet at the ground station).
- Dashboard note: the Streamlit UI reads `GET /fleet`, `GET /fleet/{aircraft_id}`,
  `GET /models` (the "Aircraft Models" section), `GET /alerts` and
  `GET /schedule/latest` (all viewer-JWT protected — see Security).

## Verified behavior (live, 2026-10-17)

- `uvicorn ground_station:app --port 8001` starts clean; DB created,
  90 aircraft seeded from `fleet_config.json`.
- POSTed the real edge report for AC-017 → **201**, `state_updated=true`;
  `GET /fleet` shows AC-017 `112.76 / 90.21 / LOW`.

  `scheduled_count=54`, `deferred_count=36`, all 90 aircraft exactly once,

  **byte-identical persisted plan** (`plan_id` included).
